# ERP 台账系统测试计划与缺陷审计

审计日期：2026-07-22  
范围：项目根目录 `README.md`、`docs` 中全部 15 个文件、`台账字段说明0716.xlsx` 的 A–D 列、当前前后端代码、现有自动化测试及运行数据库只读快照。  
约束：Excel E 列按要求忽略；所有出现“一期、二期、多期”的业务统一按最多 20 期测试。

## 一、结论

当前版本不建议直接进入生产验收。已整理出：

- 16 份文件的逐文件覆盖矩阵；
- 96 条字段规则，其中每条均有字段级用例；
- 171 条主测试用例；
- 7 类多期业务 × 14 个场景，共 98 个 20 期测试场景；
- 30 组公式与关联修改规则；
- 41 条已确认缺陷或高风险设计缺口，其中 P0 6 条、P1 30 条；
- 当前运行数据库 489 条订单明细的公式和数据质量审计。

建议先处理数据丢失、部门越权、应付公式、Decimal 精度和前端假保存等 P0，再执行全量回归。

## 二、发布阻断缺陷

| 缺陷 | 现象 | 影响 |
| --- | --- | --- |
| BUG-001 | 重置导入先执行不可回滚的 `TRUNCATE`，后续任一行失败时旧数据可能已经永久清空 | 生产业务数据丢失，接口“整批回滚”承诺不成立 |
| BUG-006 | 受限用户可用其他部门已有项目编号提交自己部门，系统可能覆盖原项目部门 | 跨部门越权、项目及既有订单被篡改 |
| BUG-002 | 仪表盘应付账款使用“采购金额－客户回款” | 核心应付 KPI 错误，采购付款判断失真 |
| BUG-003 | 前端和部分后端/导出路径把 Decimal 转为二进制浮点 | 18 位金额尾数丢失、公式和导出错误、0.01 元无法可靠结清 |
| BUG-004 | 订单详情新增采购和交付只更新浏览器内存，未调用持久化 API | 页面提示已保存但刷新丢失；同订单多明细可能串数据 |
| BUG-005 | `delivery_record` 缺少订单明细唯一约束，财务视图直接 JOIN | 重复交付可把订单、采购、毛利、应收应付和行数成倍放大 |

其它重要缺陷包括：96 字段规范与 87 列旧模板不兼容；Excel 导入绕过 API 校验；父金额调低后可产生负应收/应付；回款占比约 100 倍错位；第 501 条起被前端漏掉；关闭订单数按明细行统计；原始 Excel 重复表头覆盖审计数据；期次 1–20 没有数据库约束。

## 三、Excel 字段与公式关联修改建议

### 1. 字段规则

- A 列作为功能模块；括号内的周航、王淼作为负责人。
- B 列共识别 96 个业务字段。
- C、D 列作为类型、格式、公式、固定选项和可空规则。
- 仅明确标记“可以为空/可为空”的字段按可空处理，其余字段均应在页面、API、导入三条路径验证必填。
- E 列不纳入本次要求和测试判定。

### 2. 公式必须改为单一可信来源

建议数据库仅保存必要基础值，派生字段由服务端 Decimal 统一计算并返回；页面将派生字段设为只读，导入和 API 共用同一领域校验器。

| 目标字段 | 建议统一口径 |
| --- | --- |
| 销售/采购含税单价 | 不含税单价 × (1 + 税率/100)，保留 6 位 |
| 销售/采购金额 | 数量 × 对应单价，按确定的 `ROUND_HALF_UP` 保留 2 位 |
| 交付收入/价值/成本 | 累计有效交付数量 × 对应销售/采购单价 |
| 待交付数量/金额 | 订单数量/金额－累计有效交付数量/金额，不得为负 |
| 待签采购合同金额 | 含税采购金额－累计有效合同签订金额 |
| 财务应付 | 含税采购金额－累计有效财务入账付款 |
| 采购应付 | 含税采购金额－累计有效采购付款；不得与客户回款混用 |
| 不含税毛利润 | 不含税订单金额－不含税采购金额 |
| 不含税毛利率 | 分母为 0 时返回 0；否则毛利润/不含税订单金额 × 100% |
| 待开发票金额 | 销售订单金额－累计有效销售开票金额 |
| 已交付未开票 | 累计有效交付价值－累计有效销售开票金额 |
| 回款占比 | 回款金额/明确的发票分母 × 100；必须先冻结多发票分母口径 |
| 回款合计/应收 | 累计有效回款；销售订单金额－回款合计 |
| 关闭状态 | 对外统一使用“计算应收为 0”的状态；原始状态仅留痕 |

### 3. 当前公式审计结果

当前运行库共有 23 个项目、89 个订单、489 条有效订单明细、489 条销售发票、71 条销售回款、69 条采购付款。

| 核对项 | 差异数 | 影响 |
| --- | ---: | --- |
| 不含税订单金额 | 3 | 收入、毛利、应收相差 0.01 元 |
| 不含税采购金额 | 8 | 成本、毛利、应付不一致 |
| 含税采购金额 | 5 | 采购成本和应付不一致 |
| 交付相关公式 | 135 | 其中待交付不含税金额 133 条不一致 |
| 回款占比 | 70/70 条可比记录 | 存储约为 1、公式期望约为 100，比例口径整体错位 |
| 原始关闭状态 | 66 个订单 | 列表、筛选、导出和仪表盘可能互相矛盾 |

此外，489 条有效明细中有 14 条货物名称为空；按现有 API 判重键存在 60 个重复组、141 条额外明细。销售/采购税率尚无历史回填，财务发票校验和财务入账付款表当前也没有记录，说明 0716 新增字段尚未完成数据迁移。

## 四、极值与边界值

| 类型 | 有效边界 | 无效边界/异常值 | 预期 |
| --- | --- | --- | --- |
| 金额 `DECIMAL(18,2)` | `0.00`、`0.01`、`9999999999999999.99` | `-0.01`、最大值+0.01、3 位小数、NaN、Infinity | 合法值逐位保留；非法 422；无 500 或部分落库 |
| 数量 `DECIMAL(20,6)` | `0`、`0.000001`、`99999999999999.999999` | `-0.000001`、最大值+最小单位、7 位小数 | API 与数据库边界一致；当前 API 错误使用 18 位总数需修正 |
| 单价 `DECIMAL(18,6)` | `0`、`0.000001`、`999999999999.999999` | 负值、溢出、第 7 位小数 | 保留 6 位；派生金额溢出须提前返回 422 |
| 比例 | `0`、`0.000001`、`0.5`、`1`、`1.000001`、`13`、`100` | 负值、`100.000001`、7 位小数 | 内部统一百分数；UI 不得把合法的 0.5%/1% 再乘 100 |
| 日期 | 合法闰日、`2099-12-31` | 非法日期、`2100-01-01`、上海时区凌晨临界 | 统一 `YYYY-MM-DD`，不得产生 UTC 前一天 |
| 期次 | 1、19、20 | 0、负数、21、小数、文本 | 所有 API、导入、恢复、脚本和数据库都限制 1–20 |
| 文本 | 各列上限-1、上限、中文、emoji | 上限+1、全空格、控制字符、NUL | 按字符校验，必填字段 trim 后非空 |
| 累计金额 | 上限-0.01、刚好等于上限 | 上限+0.01、父金额下调到小于累计 | 等于可结清，超过拒绝，父记录更新也要复核子项 |

特别要测“最大数量 × 最大单价 × 税率”：虽然各输入可能单独合法，派生金额可达到约 `1e24`，远超金额列上限。系统必须在写数据库前返回字段级 422，而不是数据库 500。

## 五、20 期测试策略

以下 7 类业务全部执行相同矩阵：采购收票、入库、财务发票校验、财务入账付款、采购付款、销售开票、销售回款。

每类至少覆盖：

1. 第 1、19、20 期新增成功；第 21 期明确拒绝。
2. 满 20 期后允许修改第 20 期，但不允许新增。
3. 删除第 2 期和第 20 期后再补录，按冻结后的“编号上限/有效记录上限”规则验收。
4. 第 19 期并发两个新增请求，只允许一个得到第 20 期。
5. 同一父记录相同期次拒绝，不同父记录相同期次允许。
6. 软删除后合计、应收应付、仪表盘和导出只汇总有效记录。
7. API、Excel 导入、备份恢复和内部脚本都不能绕过 1–20。
8. 存在第 3–20 期时，87 列模板不得被宣传为无损备份；导出再导入不能静默丢期次明细。

## 六、执行计划

1. 规范冻结：统一分页 200/500、MySQL 版本、后端端口、导入方式、税率单位、舍入模式、回款比例分母和软删除补录规则。
2. 建立隔离测试库和五类角色账号，固定 `Asia/Shanghai`，确认备份可恢复。
3. 修复并自动化 P0：导入原子性、越权、应付 KPI、Decimal 精度、持久化、重复交付。
4. 周航、王淼按字段矩阵执行 96 个字段的必填、格式、边界和权限验证。
5. 财务与开发执行 30 组公式联动，并对 489 条当前数据形成修复前后差异清单。
6. 执行 98 个多期场景及并发、导入、恢复、模板往返测试。
7. 端到端 UAT：订单→采购→交付→开票→付款/回款→台账/仪表盘/导出。
8. 发布门禁：P0=0；财务/数据类 P1=0；其余 P1 有批准计划；全量回归通过；备份恢复演练通过。
