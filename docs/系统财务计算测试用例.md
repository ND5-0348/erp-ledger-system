# ERP 台账系统财务计算测试用例

## 1. 目的与判定原则

本用例用于验证订单、采购、销售、台账及仪表盘的财务数据。每个写操作均须同时验证以下四项；HTTP 状态码为 2xx 不是通过条件。

1. 接口返回的业务字段和计算字段正确。
2. 明细表的新增、更新或软删除状态正确。
3. `v_order_line_finance`、`v_project_ledger_summary` 以及仪表盘汇总随明细变化正确。
4. 成功操作产生一条审计日志；失败操作不产生业务数据和成功审计日志。

金额使用两位小数，数量与单价使用至多六位小数。比较金额时必须使用十进制定点值，不使用浮点数比较。

## 2. 计算口径与通用检查

| 指标 | 期望公式 |
| --- | --- |
| 已回款合计 | 所有 `deleted_at IS NULL` 的 `sales_receipt.receipt_amount` 之和 |
| 应收账款 | `order_value - 已回款合计` |
| 已付款合计 | 所有 `deleted_at IS NULL` 的 `purchase_payment.payment_amount` 之和 |
| 应付账款 | `purchase_amount - 已付款合计` |
| 不含税毛利 | `revenue_no_tax - cost_no_tax` |
| 含税毛利 | `order_value - purchase_amount` |
| 项目汇总 | 该项目下有效订单明细的上述指标之和 |
| 关闭状态 | 项目汇总的应收账款等于 `0.00` 时为 `closed`，否则为 `open` |

除非用例另有说明，写入后至少执行下列核对：

```sql
SELECT order_line_id, order_value, purchase_amount, total_received, total_paid,
       accounts_receivable, accounts_payable, gross_profit_no_tax, gross_profit
FROM v_order_line_finance
WHERE order_line_id = :order_line_id;

SELECT project_code, order_amount, purchase_amount, total_received,
       accounts_receivable, accounts_payable, gross_profit_no_tax, gross_profit,
       computed_close_status
FROM v_project_ledger_summary
WHERE project_code = :project_code;

SELECT action_name, status, detail
FROM operation_log
WHERE detail LIKE CONCAT('%', :record_id, '%')
ORDER BY id DESC;
```

失败请求在发送前记录相关表的总行数、有效行数和目标订单的汇总值；响应后必须完全相同。对于批量请求，任何一项失败均须验证整批没有落库。

## 3. 固定基准数据

为避免受已有业务数据影响，执行前使用唯一后缀，例如 `20260714-001`。以下数据在正常用例中复用。

| 字段 | 值 |
| --- | --- |
| 项目编号 / 订单号 | `QA-20260714-001` / `SO-QA-001` |
| 部门 / 客户 / 货物 | `测试部` / `测试客户` / `测试设备-A` |
| 订单日期 | `2026-07-14` |
| 数量 | `10.000000` |
| 销售单价（不含税 / 含税） | `100.000000` / `113.000000` |
| 不含税收入 / 订单金额 | `1000.00` / `1130.00` |
| 采购单价（不含税 / 含税） | `70.000000` / `79.100000` |
| 不含税成本 / 采购金额 | `700.00` / `791.00` |
| 交付数量 / 交付金额 | `5.000000` / `565.00` |
| 待交付数量 / 待交付金额 | `5.000000` / `565.00` |

初始财务视图的正确结果为：`gross_profit_no_tax=300.00`、`gross_profit=339.00`、`total_received=0.00`、`accounts_receivable=1130.00`、`total_paid=0.00`、`accounts_payable=791.00`。以下“仪表盘增量”指相对此项目写入前的变化，不受其他测试数据影响。

## 4. 正常输入且结果正确

| 编号 | 操作与输入 | 计算结果及数据变化断言 |
| --- | --- | --- |
| N-01 | 以基准数据调用 `POST /api/orders`。 | 新增 1 个 `project`、1 个 `sales_order`、1 个 `order_line`；并新增或更新 1 个 `purchase_info` 与 1 个 `delivery_record`。财务视图必须等于基准结果；项目台账的订单金额 `1130.00`、采购金额 `791.00`、应收 `1130.00`、应付 `791.00`、含税毛利 `339.00`，状态 `open`。仪表盘的订单金额增 `1130.00`、毛利增 `339.00`、订单数增 1、应收增 `1130.00`、应付增 `791.00`。`operation_log` 新增 `create_order`，after 快照含订单金额。 |
| N-02 | 对 N-01 的明细新增采购合同：签约 `791.00`、未签 `0.00`。 | `purchase_contract` 新增 1 行，金额字段精确保存。采购详情的合同列表有该记录，`purchase_contract_signed_amount=791.00`；应收、应付、毛利和仪表盘指标均不变。日志新增 `create_purchase_contract`，after 快照正确。 |
| N-03 | 新增采购收票：金额 `791.00`、日期 `2026-07-15`。 | `purchase_invoice` 新增 1 行，`phase_no=1`，日期及文本日期一致。采购详情的发票合计/列表包含 `791.00`；应付、毛利及项目台账财务指标不因收票而变化。日志新增 `create_purchase_invoice`。 |
| N-04 | 新增第一期采购付款：应付日期和付款日期 `2026-07-20`，金额 `300.00`。 | `purchase_payment` 新增 `phase_no=1`，应付日期保留。视图 `total_paid=300.00`、`accounts_payable=491.00`；项目台账应付也为 `491.00`；仪表盘应付减少 `300.00`。日志新增 `create_purchase_payment`。 |
| N-05 | 新增第二期采购付款：付款日期 `2026-07-25`，金额 `491.00`。 | 新增记录 `phase_no=2`，且第二期 `due_payment_date IS NULL`。视图 `total_paid=791.00`、`accounts_payable=0.00`；项目台账和仪表盘应付均为 `0.00`。不能将采购收票金额或采购金额改写为付款金额。 |
| N-06 | 新增销售合同：合同金额 `1130.00`、未签 `0.00`。 | `sales_contract` 新增 1 行；销售详情 `sales_contract_value=1130.00`。应收、应付和毛利均不变；日志为 `create_sales_contract`。 |
| N-07 | 新增第一期销售开票：金额 `565.00`、待开票 `565.00`、已交付未开票 `0.00`。 | `sales_invoice` 新增 `phase_no=1`。财务视图 `sales_invoice_amount=565.00`，销售详情显示输入的待开票/已交付未开票金额；应收、应付、毛利均不变。 |
| N-08 | 新增第一期回款：金额 `400.00`、比例 `35.398230`、日期 `2026-07-30`。 | `sales_receipt` 新增 `phase_no=1`。视图 `total_received=400.00`、`accounts_receivable=730.00`；项目台账同步，仍为 `open`；仪表盘应收减少 `400.00`，已关闭订单数不增加。日志为 `create_sales_receipt`。 |
| N-09 | 新增第二期回款：金额 `730.00`、比例 `64.601770`。 | 新增 `phase_no=2`；视图 `total_received=1130.00`、`accounts_receivable=0.00`，项目台账状态变为 `closed`；仪表盘应收减少至 0、已关闭订单数增加 1。订单金额、采购金额及毛利不得变化。 |
| N-10 | 将 N-04 的付款金额由 `300.00` 修改为 `250.00`。 | 同一 `purchase_payment.id` 被更新，不能新增付款行；`total_paid=741.00`、`accounts_payable=50.00`。日志 `update_purchase_payment` 同时保存修改前 `300.00` 和修改后 `250.00` 快照。 |
| N-11 | 删除 N-09 的第二期回款。 | 目标 `sales_receipt.deleted_at` 非空，物理行仍存在；销售详情仅剩第一期。视图恢复为 `total_received=400.00`、`accounts_receivable=730.00`，项目状态回到 `open`，仪表盘已关闭订单数减少 1。日志 `delete_sales_receipt` 保存删除前快照。 |
| N-12 | 删除该订单唯一的订单明细。 | `order_line.deleted_at` 非空；因无有效明细，`sales_order.deleted_at` 也非空。该明细不能再出现在订单、采购、销售、财务视图、台账或仪表盘汇总中；相关项目汇总不再计入此订单。日志为 `delete_order`。关联财务明细不要求物理删除，但必须因订单明细失效而不参与任何汇总。 |

## 5. 超大值与边界值

| 编号 | 操作与输入 | 计算结果及数据变化断言 |
| --- | --- | --- |
| B-01 | 创建订单，金额字段填 `9999999999999999.99`，其余必填字段合法。 | `DECIMAL(18,2)` 与接口 `Money(max_digits=18, decimal_places=2)` 的最大合法值，必须准确保存和返回，不能显示为科学计数法、`Infinity` 或发生舍入。采购金额设 `0.00` 时，视图与台账的订单金额、应收和毛利均为该值。 |
| B-02 | 创建订单，数量填 `999999999999.999999`，单价字段填 `999999999999.999999`，金额字段明确填合法最大值。 | 六位小数及 `PreciseNumber(max_digits=18)` 的边界值应原样持久化。若系统声明“数量 × 单价自动计算金额”，还必须以十进制定点计算并拒绝溢出；当前接口以传入的金额为准，因此本用例同时核对金额不会被浮点计算篡改。 |
| B-03 | 金额分别填 `0.00`，数量填 `0.000000`，回款比例分别填 `0.000000` 与 `100.000000`。 | 这些为允许下界，均可落库；视图计算应精确保持 0。零金额回款使应收保持订单金额，不能被误判为已回款或关闭；比例 100 不会改变回款金额计算口径。 |
| B-04 | 日期填 `2099-12-31`；列表查询分别使用 `limit=1`、`limit=500`、`offset=0`。 | 日期和分页边界应成功。日期原样入库；返回条数不超过指定 limit，且相同筛选条件下分页不重不漏。查询不应改变任何业务表或审计日志。 |
| B-05 | 对采购付款新增两期后，删除第二期并再次新增付款；销售回款执行相同操作。 | 新记录的期次必须为 3，不能复用被软删除的期次 2；有效期次唯一约束仍成立。金额汇总只统计有效记录，删除记录不参与应付/应收。 |
| B-06 | 同一订单并发新增两笔付款或两笔回款。 | 两个请求均成功时必须获得不同的连续期次；若一个请求因并发冲突失败，失败请求不落库且不产生成功日志。最终有效期次不可重复，应付/应收等于所有成功记录金额之和。 |
| B-07 | 已回款 `1129.99` 后，再录入 `0.01`；已付款 `790.99` 后，再录入 `0.01`。 | 回款后应收从 `0.01` 精确变为 `0.00` 并关闭；付款后应付从 `0.01` 精确变为 `0.00`。不得因二进制浮点误差显示 `-0.00`、`0.0000000001` 或错误的关闭状态。 |
| B-08 | 已回款 `1130.00` 时再次录入 `0.01`；已付款 `791.00` 时再次录入 `0.01`。 | 业务上不得形成负应收/负应付：请求应被拒绝，原有汇总保持应收、应付均为 `0.00`，无新增分期行和成功日志。此为财务完整性边界，不能仅因返回 2xx 就判通过。 |

## 6. 非法输入与原子性

| 编号 | 操作与输入 | 期望结果及“无数据变化”断言 |
| --- | --- | --- |
| I-01 | 任一金额字段填负数，例如订单金额 `-0.01`、付款金额 `-1.00` 或回款金额 `-1.00`。 | 返回 422 和字段级中文错误提示。目标业务表总行数、有效行数、财务视图、项目台账和仪表盘均与请求前一致；没有成功审计日志。 |
| I-02 | 金额填 `100.001`、`99999999999999999.99`、`NaN`、`Infinity` 或非数字字符串。 | 返回 422。不得发生数据库自动四舍五入、截断或隐式转换；所有相关数据和日志不变。 |
| I-03 | 数量或单价填超过六位小数，例如 `1.0000001`，或超过 18 位有效数字。 | 返回 422；订单明细、采购信息、交付记录均不新增也不更新，聚合值不变。 |
| I-04 | 日期填 `not-a-date`、`2026-02-30` 或 `2100-01-01`。 | 返回 422；不得插入日期文本字段作为替代值，业务表与审计日志不变。 |
| I-05 | 回款比例填 `-0.000001`、`100.000001` 或七位小数。 | 返回 422；不得新增回款期次，已有 `phase_no` 不变，财务视图和仪表盘不变。 |
| I-06 | 创建订单时缺少 `project_code`、`order_no`、`goods_name`、`customer_unit_name` 或 `order_value` 中任一项。 | 返回 422；不得创建“半成品”项目、订单头、订单明细、采购信息或交付记录。项目及订单总数和日志均不变。 |
| I-07 | 在同一项目和订单下重复创建相同货物及规格的订单明细。 | 返回 409；订单明细数不增加，原明细的数量、金额、采购信息、交付信息和所有汇总不被覆盖，且没有 `create_order` 成功日志。 |
| I-08 | 调用 `POST /api/orders/batch`，其中一条合法、另一条金额为 `-1.00` 或重复明细。 | 整批返回失败；合法行也不得落库。比较请求前后项目、订单头、订单明细、采购信息、交付记录的计数和对应项目汇总必须完全相同；不能出现批量成功日志。 |
| I-09 | 对不存在、已软删除的订单明细或财务记录执行新增/修改/删除。 | 返回 404；不创建孤儿合同、发票、付款或回款行，不更新任何已有记录，也不写成功审计日志。 |
| I-10 | 用无写权限角色调用订单、采购或销售写接口；用部门范围外的用户修改数据。 | 返回 403；记录的 `updated_at`、金额、`deleted_at` 及所有汇总完全不变。权限失败不应写成功审计日志。 |
| I-11 | 查询接口传 `limit=0`、`limit=501`、`offset=-1`。 | 返回 422；所有表和日志不变。不能通过错误分页参数获得额外数据或触发数据库异常。 |
| I-12 | 传入超长项目编号、订单号、合同号、发票号或含控制字符的文本。 | 应在持久化前返回 422，或按已定义的长度策略明确截断并返回截断后的值。无论策略为何，禁止 MySQL 静默截断后返回成功；数据、计算结果和审计快照必须一致。 |

## 7. 执行与验收建议

1. 每个用例使用独立的项目编号，或在事务/专用测试库中执行；不要在生产数据上直接运行破坏性用例。
2. 每个 POST、PUT、DELETE 后先检查明细表，再检查三个视图/接口，最后检查审计日志。对同一数据只校验响应体不足以发现事务、聚合或软删除问题。
3. I-01 至 I-12 和 B-08 是阻断性用例：若接口返回成功、出现负应收/负应付、部分落库或汇总改变，则判定不通过。
4. 订单金额、采购金额、交付金额目前由写入请求提供。若产品要求它们严格等于“数量 × 单价”或“订单金额 - 已交付金额”，应补充后端公式校验；否则需要在 N-01/B-02 中明确接受“以已提交金额为准”的口径，避免前后端计算不一致。
