## 一、批量导入

### 1.1 两个入口，行为完全不同

| 入口 | 接口 | 权限 | 导入模式 |
| --- | --- | --- | --- |
| 网页「订单管理 → 导入Excel」 | `POST /api/orders/import-excel`（`backend/app/routers/orders.py:407`） | `order_entry`（同文件 `:411`） | `reset=False`，**增量追加**，不删除已有数据 |
| 系统维护导入 | `POST /api/import/excel`（`backend/app/routers/system.py:16`） | `system_admin`（同文件 `:17`） | `reset=True`，**先 TRUNCATE 16 张业务表再导入**，是全量替换 |

系统维护导入不接收上传文件，固定读取服务器 `docs/2026*.xlsx`（`system.py:18-19`），是给上线初始化/运维重置用的。

**结论：日常网页导入是增量追加。** 已实测：库中 487 条时导入 20 条测试数据，结果 507 条。

### 1.2 网页导入的完整执行顺序

1. 校验后缀 `.xlsx`、非空、≤20MB（`orders.py:413-418`）。
2. **导入前自动备份**：`create_backup(conn, user, "pre_import")`（`orders.py:421-425`）。备份失败则直接取消导入，不写业务数据。
3. 打开工作簿，第 1 张工作表、第 2 行表头必须与模板 91 列完全一致，否则拒绝（`importer.py`）。
4. 从第 3 行逐行处理，每行依次：
   - 示例行跳过；整行全空跳过；
   - **非业务行跳过**并计入 `skipped_rows`（判定：缺订单号，且部门/订单日期/项目名称/货物名称/规格型号/数量/单价/订单价值/采购厂商这些业务载荷列全空）；
   - 缺项目编号或订单号**但填了业务字段** → 抛错、整批中止；
   - 部门权限校验 `can_access_department(user, 部门, require_entry=True)`，无权部门 → 整批中止（`importer.py:261`）；
   - 判重（见 1.3）；
   - 写入 `project` / `sales_order` / `order_line` / `purchase_info` / 交付 / 发票 / 回款等表。
5. 只要有**任何一行失败** → 返回 422「导入存在 N 条错误数据，已整批回滚」，**整批回滚，一条都不进**（`orders.py:436-442`）。

### 1.3 判重规则

判重键 = **项目编号 ＋ 订单号 ＋ 项目名称 ＋ 物资/服务名称 ＋ 规格型号 ＋ 数量 ＋ 单价 ＋ 采购厂商**

- 文本列 TRIM 后比较，空值与 0 视为相同（`backend/app/importer.py:670-706`）。
- 判重同时针对**账套中已有数据**和**本批次已写入的行**。
- 四条业务路径共用同一口径：Excel 导入（`importer.py:356-368`）、单条新增（`orders.py:1102`）、批量新增（`orders.py:907-922`）、批量修改（`orders.py:864-883`）。
- 规则沿革：原规则为「项目编号＋订单号＋项目名称＋物资/服务名称＋规格」，2026-09-14 经确认补入「数量＋单价」，2026-09-15 再补入「采购厂商」，目的是让同一订单下同货物分批次、不同单价、不同供应商的合法明细可以共存。

### 1.4 缺口

| 编号 | 缺口 | 影响 |
| --- | --- | --- |
| I-1 | 没有"幂等重跑"：同一文件重复上传会被判重拒绝，而不是"跳过已存在、只导新增" | 用户不敢重试；已实际发生（491 行全部判重） |
| I-2 | 没有部分成功模式：1 行脏数据挡住其余全部 | 大文件导入成功率低，排错成本高 |
| I-3 | 判重是应用层 `SELECT`，`order_line` 表**没有对应唯一索引**（`docs/erp_ledger_schema.sql:169-176` 只有主键和外键） | 并发导入可能重复入库 |
| I-4 | 错误明细截断为前 20 条（`importer.py:666`），且整条消息被拼成一行塞进前端 `alert()` | 491 条错误时无法阅读 |
| I-5 | 导入与导入前备份是两个独立事务 | 导入失败也会留下备份文件（当前是有意设计，但会加快备份堆积） |
| I-6 | 20MB 上限 + 300 秒代理超时 | 两万条级别的大文件未演练过 |

## 二、并发修改

### 2.1 结论：没有编辑期锁定，是「后提交覆盖先提交」

- **打开编辑界面只是前端状态**，服务端不知道有人在编辑，也不加锁。
- **保存是整行全字段覆盖**：前端提交完整 payload，`PUT /api/orders/{order_line_id}` 把所有列写成提交值。
- 两人同时编辑同一行 → 后保存者覆盖先保存者，**先改的人收不到任何提示**（last-write-wins）。
- 没有版本号字段，没有乐观锁。
- 隔离级别没有在代码中设置，使用 MySQL 默认的 REPEATABLE READ。

所以**不是**"一个用户修改时冻结该数据、保存后释放"的模式。

### 2.2 确实使用了行锁的位置

| 场景 | 位置 | 目的 |
| --- | --- | --- |
| 批量修改基本信息 | `orders.py:523`（`_ensure_order_line_in_conn(..., lock=True)` → `FOR UPDATE`） | 批量校验与写入的原子性 |
| 采购付款新增 | `purchases.py:1240 / 1261 / 1289 / 1319` | 付款期数 `phase_no` 递增不冲突 |
| 销售回款、发票 | `sales.py:948 / 969` | 同上 |
| 单条修改、批量新增 | **无锁** | — |

这些锁只在**单个请求的事务内**持有，请求结束（提交或回滚）即释放，**不覆盖用户的编辑过程**。

已有并发测试：`backend/tests/test_financial_integration.py:2001`（用例 B-06）用两个线程同时新增付款，断言期数为 1、2。

### 2.3 缺口

| 编号 | 缺口 | 影响 |
| --- | --- | --- |
| C-1 | 无冲突检测，并发编辑静默覆盖 | 数据丢失且无人察觉（例：A 改数量、B 改日期，B 后保存 → A 的改动消失） |
| C-2 | 列表不展示"最后修改人/时间" | 用户无法判断数据是否被别人改过 |
| C-3 | 批量编辑与单条编辑之间也无互斥 | 同上 |
| C-4 | 并发导入的判重存在竞态（同 I-3） | 重复数据入库且无数据库层兜底 |

### 2.4 可选方向（未实施，供讨论）

按成本递增三个层次，可任选或分阶段：

1. **提示层**：台账列表增加「最后修改时间/修改人」列，保存前提示"该行已被他人修改过"。
2. **乐观锁**：`order_line` 已有 `updated_at`（`docs/erp_ledger_schema.sql:168`，`ON UPDATE CURRENT_TIMESTAMP`），可直接复用或新增 `version` 列；保存时带上读取到的版本，不匹配返回 409 让用户决定。
3. **软锁**：`locked_by` + `locked_at`，进入编辑时加锁、保存或超时后释放；需要额外处理浏览器异常退出导致的悬挂锁。

## 三、数据备份与恢复

### 3.1 触发时机（全部同步执行，**没有定时任务**）

| 时机 | 备份类型 | 位置 |
| --- | --- | --- |
| 网页导入前 | `pre_import` | `orders.py:421-425` |
| 系统维护导入前 | `pre_import` | `system.py:21-24` |
| 恢复前 | `pre_restore` | `system.py:93-95` |
| 手动 | `manual` | `system.py:82-86` `POST /api/backups` |

代码库中**没有** scheduler / cron / APScheduler 之类的东西，所以"每天自动备份"目前完全依赖人工点按钮。

### 3.2 备份内容与格式

- **16 张业务表**（`backend/app/backup.py:19-36`）：`import_batch`、`ledger_raw_row`、`project`、`sales_order`、`order_line`、`purchase_info`、`delivery_record`、`purchase_contract`、`purchase_invoice`、`warehouse_entry`、`finance_invoice_check`、`finance_payment_entry`、`purchase_payment`、`sales_contract`、`sales_invoice`、`sales_receipt`。
- **不包含**：账号 `erp_user`、操作日志 `operation_log`、备份记录 `backup_record`。恢复后账号和日志保持当前状态。
- 格式：JSON + gzip，先写 `.tmp` 再原子改名（`backup.py:53-78`），避免写坏。
- 实现方式：**应用层把整表读进内存**再序列化，不是 `mysqldump`。

### 3.3 存储与恢复

- 目录：`backend/backups`，**硬编码**在 `backend/app/config.py:13`（`BACKUP_DIR = BACKEND_DIR / "backups"`），没有任何配置项。
- 恢复：`POST /api/backups/{backup_id}/restore`，只允许恢复该目录下的文件（有路径穿越校验，`backup.py:123-126`），恢复会覆盖业务表。
- 前端：系统管理页可查看备份列表、手动备份、恢复。

### 3.4 缺口（对照"每天自动 + 双硬盘双备"的目标）

| 编号 | 缺口 | 说明 |
| --- | --- | --- |
| B-1 | 无定时任务 | 代码中不存在调度器，需要新增（可考虑独立脚本 + Windows 计划任务 / cron，不必进 Web 进程） |
| B-2 | 存储路径不可配置 | `BACKUP_DIR` 是常量，无法指向第二块硬盘 |
| B-3 | 无第二副本 | 单目录单盘，盘坏即全丢 |
| B-4 | 无保留策略 | 备份文件只增不减，没有按数量/天数轮转 |
| B-5 | **备份目录与数据库不绑定** | 当前 `backend/backups/` 下有 **66 个 `.json.gz` 文件**，而 `backup_record` 表只有 **13 条记录**，即 **53 个孤儿文件**。最可能的原因是测试环境（`MYSQL_DATABASE=erp_ledger_test_*`）与本地库共用同一个备份目录：测试库跑完被 drop，记录随之消失，文件却留在磁盘上。**此项需要在写计划前确认** |
| B-6 | 无备份校验 | 不校验文件完整性、行数、可恢复性 |
| B-7 | 无失败告警 | 备份失败只在"导入前备份"这条路径上阻断流程，定时备份还需要独立的告警方式 |
| B-8 | 大库内存压力 | 整表读入内存再落盘，两万条级别需要实测 |
| B-9 | 无恢复演练记录 | 另见 `docs/部署交接_2026-09-14.md:188,261`：明确写了"没有完成全库定时备份""需要全库备份、异机保留、定时执行与恢复演练" |

## 四、账号权限

### 4.1 模型

三层结构：**权限点 → 角色默认 → 每账号覆盖 + 部门范围**。

- **权限点 10 个**（`backend/app/auth.py:20-31`）：`order_entry` / `order_edit` / `order_delete`、`purchase_entry` / `purchase_edit` / `purchase_delete`、`sales_entry` / `sales_edit` / `sales_delete`、`system_admin`。
- **角色 5 个**（`auth.py:33-39`）：`admin`、`order_entry`、`purchase_entry`、`sales_entry`、`viewer`，各自带一组硬编码默认权限。
- **每账号可覆盖**（`docs/erp_ledger_schema.sql:58-62`）：`permissions_json`（有值即覆盖角色默认，`auth.py:69-72`）、`department_scope_json`、`department_can_view`、`department_can_entry`。
- **界面**：系统管理页勾选式配置（`src/components/SystemScreen.tsx`），前端权限选项定义在 `src/lib/permissions.ts:46`。

### 4.2 现状：界面显示的角色是"反推"出来的

`SystemScreen.tsx:64` 的 `deriveRoleCode()` 只识别 5 种固定权限组合：

```
含 system_admin → admin
仅 order_entry   → order_entry
仅 purchase_entry→ purchase_entry
仅 sales_entry   → sales_entry
其它             → viewer
```

所以勾出任何非标准的权限组合，界面上的角色标签都会显示成"查看员"，**与实际权限不一致**。这是"权限设置不直观"最直接的原因。

后端 `normalize_permissions`（`auth.py:69-72`）在 `permissions_json` 为空时**静默回退**到角色默认权限，也可能造成"界面看着没权限、实际有权限"。

### 4.3 批量导入的权限现状

- 网页导入要求 **`order_entry`**（`orders.py:411`）→ **凡是能录订单的账号就能导入整份 Excel**，导入能力没有独立管控。
- 系统维护导入（全量替换）要求 `system_admin`。
- **部门隔离已经做了**：导入时逐行校验 `can_access_department(user, 部门, require_entry=True)`，遇到无权部门整批中止（`importer.py:261`）。

### 4.4 缺口

| 编号 | 缺口 | 说明 |
| --- | --- | --- |
| P-1 | 没有独立的"批量导入"权限点 | 导入能力隐含在 `order_entry` 里，无法做到"能录单但不能批量导入" |
| P-2 | 角色标签由前端反推 | 非标准组合显示为"查看员"，名实不符 |
| P-3 | 权限粒度是"模块 × 动作" | 没有功能级权限（如导入、导出、备份恢复） |
| P-4 | `permissions_json` 为空时静默回退角色默认权限 | 容易造成误解，建议改为显式行为 |
| P-5 | 权限与部门范围两个维度挤在同一屏 | 勾选约束靠提示文案兜底（如"已勾选录入权限，请同时勾选查看权限"） |

### 4.5 要做"批量导入权限隔离"需要联动改的地方

1. 新增权限点（例如 `order_import`），加进 `auth.py:20` 的 `ALL_PERMISSIONS` 和 `src/lib/permissions.ts` 的 `Permission` 联合类型。
2. 导入端点换权限：`orders.py:411` 的 `require_permission("order_entry")` 改为新权限点。
3. 前端按钮可见性：`src/components/OrdersScreen.tsx` 的「导入Excel」入口增加权限判断。
4. 决定策略细节：**已有数据的判重**（I-1）与**无权部门的行**是"整批中止"还是"跳过并报告"，这会直接影响 I-2。
5. 角色默认权限是否给 `order_entry` 角色附带 `order_import`，需要产品确认（否则现有账号会突然失去导入能力）。
