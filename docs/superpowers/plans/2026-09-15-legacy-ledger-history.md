# 旧台账兼容与历史查询实施计划（独立阶段 H）

> **For agentic workers:** When implementation is authorized, execute this plan task-by-task using executing-plans inline. A planning-only request does not authorize execution. 按复选框逐项交付；本计划交给DeepSeek实施，再由Codex独立审查。

**Goal:** 安全转换旧台账单元格中的负责人历史、订单改号历史和多期财务数据，使导入、历史搜索及金额统计保持正确。

**Architecture:** 在现有导入前增加可预览、可确认的纯解析层，输出规范化记录后复用统一写入服务；以稳定内部ID保存业务关系，当前值、历史别名及原始来源分别保存。沿用A阶段权限与写入互斥，对B阶段提供明确的版本、恢复和维护替换契约。

**Tech Stack:** Python / FastAPI / SQLAlchemy / MySQL / openpyxl；React / TypeScript；现有业务备份、期次表及测试框架。

## 2. 已确认业务规则

1. 层级为框架项目→订单→子项目→物资/服务，一个框架有多个订单，一个订单有多个子项目。
2. 客户经理属于框架项目。旧单元格 `甲/乙/丙` 按旧到新排列，丙为当前负责人；保留历史顺序，缺少历史变更日期时不编造。
3. 框架共享字段仍是客户经理、分公司、部门、三级团队。子项目共享字段是客户单位、最终用户、区域平台。
4. 订单号 `A/B/C` 是同一订单的历次改号，不是多个独立订单；C为当前订单号，A/B为历史别名。
5. 开票、收票、付款、回款日期与金额、票据/凭证号按位置一一对应。
6. 多日期对应单一金额必须人工确认每期金额，不平均拆分、不把合计复制给每一期。
7. 同一具体子项目内按物资名称、规格、销售单价、数量、采购厂商五项组合唯一；跨子项目允许相同明细。
8. 普通导入继续整批成功或整批回滚。解析歧义是预检问题，不应通过跳过有业务数据的行掩盖。

## 3. 数据与接口契约

### 3.1 当前值、历史及来源

优先复用A修正后的稳定ID，禁止以可变订单号充当内部主键。物资、子项目和财务记录始终关联同一个稳定订单。

新增表建议如下；实施前若已有同职责表，应复用并在落点表中写明映射，不重复建表：

| 建议表 | 关键内容 |
| --- | --- |
| `sales_order_number_history` | `sales_order_id`、归一化订单号、历史顺序、来源；当前号仍保存在订单主记录，历史表同时覆盖当前号用于统一查找 |
| `project_manager_history` | `project_id`、负责人名称、历史顺序、可空生效时间、来源；框架主记录保存现任 |
| `legacy_import_session` | 随机会话ID、创建人、创建时间/到期时间、模式、源文件SHA256、解析器版本、基准epoch和受影响框架版本、状态 |
| `legacy_import_source` | 会话、工作表、行列坐标、原始值、解析后结构、人工确认内容、确认人和时间；不得将真实原始值写入Git或普通日志 |

编号在同一框架内必须映射到唯一订单，历史号与其他订单当前号/历史号冲突均阻断；不同框架可存在同编号。负责人历史允许重复任职，例如甲→乙→甲不能去重成甲→乙。

不伪造历史日期：历史顺序、导入记录时间、已知生效时间三个概念分别保存。订单别名也不因缺少改号日期而丢失。

### 3.2 解析结果

新增纯函数解析模块，不在解析函数内连库或写文件。输入包含原单元格值与坐标；输出为：

```text
ParsedCell = {raw_value, tokens, issues}
Issue = {sheet, row, columns, code, message, blocking}
Phase = {source_columns, source_position, date, amount, document_no}
```

错误码至少包括 `AMBIGUOUS_DATE_SEQUENCE`、`PHASE_COUNT_MISMATCH`、`AMOUNT_SPLIT_REQUIRED`、`CURRENT_MANAGER_CONFLICT`、`ORDER_ALIAS_CONFLICT`、`ORDER_HISTORY_CONFLICT`。前端按错误码展示，不解析中文字符串作流程判断。

### 3.3 预检与提交

在现有 `/api/orders/import-excel` 继续支持无歧义标准文件；发现历史多值内容时转入预检流程，不静默降级。建议新增：

- `POST /api/orders/import-preview`：上传并解析，返回会话ID、摘要、计数和问题摘要；无业务表写入。
- `GET /api/orders/import-preview/{id}`：分页读取解析记录和错误，避免一次返回两万条；仅所属授权用户或管理员访问。
- `PUT /api/orders/import-preview/{id}/resolutions`：提交明确的逐项修正，重新执行全部校验。
- `POST /api/orders/import-preview/{id}/commit`：提交已完成预检的会话，不从浏览器再次接收任意规范化业务JSON。

会话默认24小时有效、目录独立、随机不可猜ID；原文件限20MB，不允许客户端指定磁盘路径。存在阻断问题、文件摘要改变、用户失权、基准版本变化时拒绝提交。无B版本能力时使用写锁内重新解析和重查约束作为过渡，并明确B整合未验收。

提交在A写锁内复核权限和业务规则，先按既有策略备份，再一次事务写入全部规范化记录与历史。已提交会话再次提交只返回原结果，不能再新增业务记录；新上传相同文件仍按现有重复规则报告，不自动跳过或覆盖。

维护替换复用同一解析结果，但仍需B的独立全量替换确认、基准校验和事务删除保护，不能将普通提交接口变成清库入口。
