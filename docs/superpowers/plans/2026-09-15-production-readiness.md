**Goal:** 保留维护清库导入，补齐权限、原子替换、并发冲突保护、每日双盘备份及可验证恢复能力。

## 4. 核心约定

### 4.1 写入互斥与版本

使用 MySQL 命名锁实现按数据库隔离的 `business_write()` 上下文，建议新建 `backend/app/write_guard.py`。初版允许同一数据库的业务写请求串行执行，读取不阻塞；这是事务期间锁，不是用户打开页面期间锁。

- 锁名称由数据库名的稳定摘要构成，长度不超过 MySQL 限制。不得只用 Python 进程锁。
- 持有同一数据库连接：先取得命名锁，再开启业务事务/读取快照，提交或回滚后释放。处理 SQLAlchemy autobegin，不能在取得锁前保留旧事务快照。
- 等待上限5秒，超时返回可识别的 `409 BUSINESS_WRITE_BUSY`，不写业务数据。前端保留用户输入，不自动重复提交。
- 所有订单、采购、销售新增/修改/删除、批量入口、两种导入、业务恢复必须覆盖；嵌套 helper 不重复取锁。建立端点覆盖清单。
- 异常路径必须释放锁，连接不可带锁归还连接池；释放失败则丢弃该连接。进程断开由数据库释放锁。
- 同一数据集的其他数据库写入脚本也必须使用保护入口；生产日常禁止绕过应用直接改业务表。

新增 `project.version BIGINT NOT NULL DEFAULT 1`；新增单行表 `business_state(id, data_epoch)`，该表不包含在16表业务恢复/替换中。

- 任一项目关联业务修改在同一事务递增该项目版本；批量请求同一项目可统一递增一次。
- 读取编辑数据返回 `project_version` 和 `data_epoch`，编辑保存必须带原值。缺失返回422；不匹配返回 `409 EDIT_CONFLICT`，业务表不改动。
- 修改共享项目/订单字段、采购付款/销售开票/回款等均会使该项目旧编辑页面失效。初版允许同项目不同明细产生保守冲突，提示准确说明“项目关联数据已变化”。
- 全量替换或业务恢复成功时递增 `data_epoch`，防止恢复旧版本后旧页面意外通过校验；失败不递增。
- 后端拒绝旧请求才是保护；只显示修改时间、只在前端比对或使用秒级时间戳不算完成。

### 4.2 三种不同的备份

- 应用业务备份：维持16张业务表，用于业务回退；不冒充全库备份。
- 服务器全库备份：包含业务、账号、权限、操作日志、备份记录、视图及本轮新增控制表；加密/限制访问地保存恢复所需部署配置，不把秘密打印到日志或提交Git。
- 异机副本：每周人工复制校验过的全库备份及所需恢复配置到另一台电脑，记录日期和操作者。双盘副本不能替代异机副本。
