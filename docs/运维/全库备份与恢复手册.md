## 三种副本

|副本|内容|用途|
|---|---|---|
|应用业务备份|20 张业务表，包含子项目、订单号历史、负责人历史和已提交旧台账的原始/确认来源|系统页面的业务回退；账号、权限、操作日志和外部数据代次不回退|
|服务器全库备份|配置指定的整个应用数据库：业务、账号、权限、日志、备份记录、会话/控制表、视图、例程、事件、触发器|服务器故障或数据库整体恢复；不是 MySQL 实例所有数据库的备份|
|每周异机副本|已校验的全库文件及清单，另行受控保存恢复配置|应对两块本机磁盘同时损坏；双盘不能替代异机副本|

恢复配置至少包括部署版本/镜像标识、Compose 配置、应用环境配置和数据库连接配置。秘密文件须与备份一样受限访问，禁止放入 Git、工单或普通日志；加密后另行保存密钥。当前脚本不会读取或输出业务 `.env`，配置副本由运维按实际部署目录准备并登记。

## 安装前只读核对

在实际服务器收集以下输出，再填写 `ops/backup/backup.env.example`，不要根据设备名称猜第二块磁盘，也不要格式化或修改挂载。

```sh
lsblk -f
findmnt
df -h
docker compose ps
```

确认：主副目录位于两个不同物理磁盘；第二盘真实挂载点、UUID 与配置一致；目录已由运维创建并限制为 0700；恢复配置副本另存于同样受控的位置；MySQL 服务和容器内 mysqldump 都为 8.4；应用库普通表全部为 InnoDB。

容器内创建只读挂载的客户端选项文件，权限 0600，配置 `[client]` 下的连接信息。`MYSQL_CLIENT_CNF` 指向该容器内文件。密码不放进命令行或 `backup.env`。备份账号需要读取表、视图、触发器及例程/事件所需权限，由 DBA 按实际对象配置。脚本使用一致性事务快照；备份期间禁止执行 DDL。参数及权限依据 [MySQL 8.4 mysqldump 官方文档](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html)。

## 审批后的安装顺序

1. 将 `ops/backup` 中脚本复制到 `/opt/erp-ledger-backup`，由 root 管理，普通应用账号不可修改。Python 3、Docker CLI、findmnt、lsblk 必须可用。
2. 将填好的配置安装到 `/etc/erp-ledger-backup/backup.env`，权限 0600。第二盘路径和 UUID 留空时脚本直接失败，不会假报双盘成功。
3. 手动执行一次 `bash /opt/erp-ledger-backup/full-backup.sh`，核对两个目录里的同名 `.sql.gz` 和 `.manifest.json`。
4. 分别执行 `verify-backup.sh /绝对路径/备份.sql.gz`，再执行 `check-backup-age.sh`。gzip/摘要校验仅证明文件完整，必须另做恢复演练。
5. 将四个 systemd 单元文件安装到 `/etc/systemd/system`，先 `systemd-analyze verify` 与 `systemd-analyze calendar '*-*-* 02:00:00 Asia/Shanghai'` 检查服务器支持，再 reload 并启用两个 timer。此步骤需后续生产授权，目前没有执行。

每天北京时间 02:00 备份，错过执行会补跑；每小时检查最近成功双副本是否超过 26 小时。Python 使用同一个状态目录内的 flock 防止重叠。默认保留最近 30 天及最近 12 周每周一份；仅在本次双副本校验成功后轮转，仅删除具有有效清单且两边均可验证的过期配对文件。孤儿、未知文件、单边幸存文件不自动删除。

## 故障与值班检查

查看 `STATE_DIR/status.json`、`last-success.json`、`health.json` 和对应 service 的 journal。

- `success`：本次主副盘均校验通过。
- `partial`：主盘文件保留，但第二盘或后续步骤失败。进程非零退出；副盘失败不更新最后成功时间。
- `failed`：预检、dump 或主盘写入失败，不覆盖上次成功记录。
- 第二盘未挂载、UUID 不符、同物理盘、空间不足、非 InnoDB 或版本不符都会拒绝运行。

可选 `NOTIFY_HOOK` 为本机经审查的可执行文件，只接收脱敏状态文件路径。未配置时没有主动消息通知，值班人必须每日检查 service 状态和最新成功时间。文件权限限制不等于加密；移动或带离服务器前按单位要求加密。

## 隔离恢复与正式切换

1. 记录演练开始时间。正式恢复前停止应用写入，保留当前全库与配置副本。
2. 校验选定文件及清单，核对源库、时间、版本、摘要，记录操作人。不要直接把 SQL 导入当前生产连接。
3. 在**新隔离 MySQL 8.4 实例**中创建空数据库。可沿用源库名以保留视图、例程中的库名引用，但实例、数据卷、网络必须独立，不能复用生产卷。客户端选项文件只能连接这个演练实例。
4. 将校验过的 gzip 解压流交给隔离实例的 mysql 客户端；Bash 须启用 `set -euo pipefail`，检查解压和 mysql 两个退出码。不要随意对真实 dump 做字符串替换迁移库名。
5. 启动隔离应用，使用独立 AUTH_SECRET；核对账号登录、权限和部门限制、业务表行数、销售/采购/开票/回款总额、视图、订单号历史、负责人历史、来源记录及期次。
6. 应用业务恢复会递增外部 `data_epoch`；**全库恢复连控制表也回退，正式重新开放前必须轮换 AUTH_SECRET 使所有旧会话失效**。验证重新登录后旧编辑页面不能提交，重新加载编辑上下文。
7. 经批准才切换应用连接；检查上述指标后开放服务。记录数据库与配置恢复总耗时，目标少于 24 小时。保留原库直至回退窗口结束。
